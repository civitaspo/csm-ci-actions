# Merge

Reusable client callers declare and map only `CSM_CI_CLIENT_APP_PRIVATE_KEY`. See the [secret contract and staged migration](setup.md#explicit-secret-contract-migration) for server feature credentials and compatible caller pins.

`/merge` asks csm-ci to squash-merge the current head of an open pull request. The command takes no argument. It is accepted only from an account listed in `trust.mergers`, or from a bot listed in `trust.bot_mergers` when that bot authored the pull request and every commit.

At acceptance the server checks the pull request state and the S5 trust rules: the commenter is an authorized merger, a Bot request meets the Bot rules, the comment is unedited and recent, the head predates the comment, and no Server receipt exists. These checks reload the configuration from the server repository's current default branch and confirm that the repository still enables merge. An accepted request then merges by one of two paths: [platform auto-merge](#platform-auto-merge) or the [self-merge fallback](#self-merge-fallback).

## Platform auto-merge

`repositories[].merge.use_platform_automerge` is an optional boolean that defaults to `true`. The server tries this path when it is not `false`. It first reads the repository's GraphQL `autoMergeAllowed` and the rules that apply to the default branch with the read token (`GET /repos/{owner}/{repo}/rules/branches/{branch}`). They must include an active `pull_request` rule with at least one required approval and `dismiss_stale_reviews_on_push: true`, and an active `required_status_checks` rule containing `csm-ci/policy` from the Server App and every configured required check with its App ID. If the pull request is already mergeable, with `mergeStateStatus` `CLEAN`, `UNSTABLE`, or `HAS_HOOKS`, the server runs one complete readiness validation, posts no wait notice, and squash-merges with the retry rules below. Otherwise it calls GraphQL `enablePullRequestAutoMerge` with `SQUASH`, the pinned head as `expectedHeadOid`, and the commit headline and body described below. It then posts the receipt and ends. If auto-merge is already enabled by the Server bot, matched by immutable ID and type `Bot`, with method `SQUASH`, the server posts the same receipt without another call. Auto-merge enabled by anyone else or with another method fails the request with a receipt.

After enabling, GitHub merges when the ruleset is satisfied: the configured approver's approval, `csm-ci/policy`, and each configured required check. The server does not poll, revalidate, or apply a deadline after enabling. A push dismisses the approval, so `csm-ci/policy` fails until the new head is approved. The server does not disable auto-merge on a push, a force push, or an edit or deletion of the command comment. The comment checks apply only at acceptance. After enabling, nothing rechecks merger trust, Bot ownership, `allow_bot_requests`, or configuration changes; only the ruleset and the latest `csm-ci/policy` result gate the merge. If GitHub later cancels the auto-merge, the server posts nothing. GitHub accepts enabling only when the repository has `allow_auto_merge: true`; see [Repository settings](repo-settings.md#configuration).

## Self-merge fallback

The server runs its own merge process instead when any of these holds:

- `merge.use_platform_automerge` is `false`.
- `autoMergeAllowed` is `false` for the repository.
- The branch rules check fails.

The server decides this at acceptance, before it mints the final token. If the final step's configuration now sets `use_platform_automerge: false`, it skips enabling and merges only when one readiness validation passes. When enabling later fails, a GraphQL error saying the pull request is in clean, unstable, or has_hooks status means it became mergeable meanwhile, and the server merges it directly as above. For any other error, including a lost response, the server rereads the auto-merge state and treats the request as enabled only when the Server bot enabled it with `SQUASH`; otherwise the request fails with a receipt.

Before it starts waiting, in every fallback case including `use_platform_automerge: false`, the server posts one comment with the marker `<!-- csm-ci:merge-wait:<comment_id> -->`. The comment states that platform auto-merge is not in use and csm-ci's own merge process is running, gives the reason, and gives the deadline in UTC: 60 minutes after the command comment was created, when the comment itself expires. It says the pull request is merged if approval and checks are ready by then and otherwise fails with a receipt. A replay does not post a second notice.

Every readiness validation reloads the configuration, re-reads the pull request and command comment, evaluates the current policies against GitHub state, checks that the latest review from the configured approver is an approval for the pinned head, and verifies each configured required check by name and GitHub App ID. A required check passes only with a `success` or `skipped` conclusion. Readiness does not use GitHub's `reviewDecision` or the `csm-ci/policy` check run result, so it follows the current configuration even when that changed after the check ran. A moved head, invalidated comment, removed merger, changed policy, or failed trust check aborts the request. Readiness polling runs every 30 seconds until that deadline. This fixed limit has no setting; a leftover `merge.deadline_minutes` key fails strict configuration parsing, so remove it when upgrading.

## Tokens, commit message and receipts

Notification tokens have issues and pull-requests write access because GitHub requires pull-request permission for PR comment reactions and receipts; they have no contents write access. The server mints fresh read and notification tokens after readiness succeeds, then mints its final token with contents, pull-requests, and workflows write access for the target repository. This final token includes workflows write for every ready pull request so approved `.github/workflows/**` changes can merge without a separate path-detection decision. Read and notification tokens have no workflows write access.

In either path the server enables auto-merge or merges with its final token. In the fallback and in the immediate merge it revalidates readiness before calling GitHub's squash merge endpoint with the pinned head SHA. HTTP 405, 422, and 503 responses are retried only after another complete validation. HTTP 409 fails immediately. A successful response must report `merged: true`. The additional permission does not bypass trust, command evidence, approval, policies, or required checks, and does not change securefix's `allow_workflow_changes` setting.

The squash commit title is the pull request title followed by ` (#<number>)`, as in a squash merge from the GitHub web UI. The commit message is the pull request body. Auto-merge freezes both at enabling time, so later edits to the title or body do not change them. Duplicate `Co-authored-by` lines in the body are removed. The server posts a receipt containing `<!-- csm-ci:merge:<comment_id> -->` after an accepted command succeeds, fails, or enables auto-merge. Requests rejected before acceptance do not receive a receipt. If a long wait fails after the initial notification token expires, the workflow mints a fresh notification token and retries the idempotent failure receipt. A receipt authored by the Server bot prevents replay.

Result comments keep the outcome, failure reason, and corrective action at normal size. Success explicitly reports a squash merge. An auto-merge receipt reports that platform auto-merge was enabled for the pinned head and is not a merge result; its footer links the command, the pinned head, and the run. A separate `<sub>` footer contains HTML links to the original command, the pinned head with a short SHA, the resulting squash commit on success, and the actual server workflow run and attempt. Failure comments ask the reader to resolve the failure, confirm approval and checks for the current head, and post a new exact `/merge` comment. They do not claim an automatic rebase or a future retry. The existing receipt marker and replay suppression remain unchanged.

Wait mode exposes the pinned head at acceptance so a fresh-token failure receipt can link the original head even if readiness later fails or the head changes. This metadata does not change acceptance timing or final readiness revalidation.

The client workflow listens for newly created pull request comments whose body is exactly `/merge`. The commenter must have OWNER, MEMBER, or COLLABORATOR association, or be a Bot whose immutable ID matches the pull request author. This Bot exception only forwards a request. The server independently requires an enabled repository, an allowed bot merger, and every commit authored by that bot, followed by current approval, policy and CI checks. `repositories[].merge.allow_bot_requests: false` rejects Bot requests for a repository; no repository is restricted by name. See the [repository policy contract](policy-check.md#effective-repository-policy-resolution). Approval and recheck comments retain their association requirement.

`bun e2e/run.ts --ref <sha> --feature merge` exercises the merge scenarios against the testing repositories, including an explicitly approved workflow change and its exact merged content. The fallback scenarios set `use_platform_automerge: false`; the 60-minute limit is covered by unit tests only.

A deployed server workflow that omits workflows write from its final merge token cannot merge the workflow change that upgrades that token. If `controlled-merges` permits only the Server App, an operator merge cannot bypass that restriction. Bootstrap requires a concrete, separately authorized recovery procedure under [break glass](repo-settings.md#break-glass), with the affected settings saved and protection restored afterward. This specification does not authorize changing App permissions or disabling protection.

## Repository permission for Bot requests

The runtime accepts optional `repositories[].merge.allow_bot_requests`. Omission permits consideration under global Bot trust. `false` rejects Bot requests independently of global `trust.bot_mergers` membership and sensitive-path exemptions. The first matching repository entry supplies this setting. `true` still requires membership by immutable ID, ownership of the PR and every effective commit identity, current approval, effective policies, and required checks. The Server App executes every accepted merge regardless of who requested it.

`/approve`, `/recheck` and policy-check share one concurrency group per pull request because they publish policy checks and reports. Other kinds, including `/merge`, keep their own group, so a waiting `/merge` does not block `/approve`, `/recheck` or policy-check, and both can be posted together. Every readiness validation and the final revalidation use the current effective repository settings. Revoking Bot permission while a self-merge request waits must prevent its merge; an enabled auto-merge is governed by the ruleset only. Explicit protection for the server and actions repositories uses `allow_bot_requests: false` together with all-path sensitivity and no exemptions. Those entries must stay in the Server configuration; the runtime no longer adds this protection by name. Any subsequent relaxation requires a separate configuration diff and live verification.

A repository with `allow_bot_requests: false` rejects Bot requests before acceptance, without a rocket or receipt. Revocation after acceptance aborts readiness or final validation and posts the existing failure receipt. Human merger authorization is unaffected by this Bot setting.
