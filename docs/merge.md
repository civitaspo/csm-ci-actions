# Merge

Reusable client callers declare and map only `CSM_CI_CLIENT_APP_PRIVATE_KEY`. See the [secret contract and staged migration](setup.md#explicit-secret-contract-migration) for server feature credentials and compatible caller pins.

`/merge` asks csm-ci to squash-merge the current head of an open pull request. The command takes no argument. It is accepted only from an account listed in `trust.mergers`, or from a bot listed in `trust.bot_mergers` when that bot authored the pull request and every commit.

The server checks the pull request state and the S5 trust rules before waiting. Every readiness validation reloads the configuration from the server repository's current default branch and confirms that the repository still enables merge. It then re-reads the pull request and command comment, evaluates the current policies against GitHub state, checks that the latest review from the configured approver is an approval for the pinned head, and verifies each configured required check by name and GitHub App ID. A required check passes only with a `success` or `skipped` conclusion. Readiness does not use GitHub's `reviewDecision` or the `csm-ci/policy` check run result, so it follows the current configuration even when that changed after the check ran. A moved head, invalidated comment, removed merger, changed policy, or failed trust check aborts the request. Readiness polling runs every 30 seconds, or every twelfth of `merge.deadline_minutes` when that is shorter, until the deadline expires. A short testing deadline polls more often, while a deadline of 6 minutes or more keeps the 30 second interval.

Notification tokens have issues and pull-requests write access because GitHub requires pull-request permission for PR comment reactions and receipts; they have no contents write access. The server mints fresh read and notification tokens after readiness succeeds, then mints its final token with contents, pull-requests, and workflows write access for the target repository. This final token includes workflows write for every ready pull request so approved `.github/workflows/**` changes can merge without a separate path-detection decision. Read and notification tokens have no workflows write access.

The server revalidates readiness before calling GitHub's squash merge endpoint with the pinned head SHA. HTTP 405, 422, and 503 responses are retried only after another complete validation. HTTP 409 fails immediately. A successful response must report `merged: true`. The additional permission does not bypass trust, command evidence, approval, policies, or required checks, and does not change securefix's `allow_workflow_changes` setting.

The squash commit title is the pull request title followed by ` (#<number>)`, as in a squash merge from the GitHub web UI. The commit message is the pull request body. Duplicate `Co-authored-by` lines in the body are removed. The server posts a receipt containing `<!-- csm-ci:merge:<comment_id> -->` after an accepted command succeeds or fails. Requests rejected before acceptance do not receive a receipt. If a long wait fails after the initial notification token expires, the workflow mints a fresh notification token and retries the idempotent failure receipt. A receipt authored by the Server bot prevents replay.

Result comments keep the outcome, failure reason, and corrective action at normal size. Success explicitly reports a squash merge. A separate `<sub>` footer contains HTML links to the original command, the pinned head with a short SHA, the resulting squash commit on success, and the actual server workflow run and attempt. Failure comments ask the reader to resolve the failure, confirm approval and checks for the current head, and post a new exact `/merge` comment. They do not claim an automatic rebase or a future retry. The existing receipt marker and replay suppression remain unchanged.

Wait mode exposes the pinned head at acceptance so a fresh-token failure receipt can link the original head even if readiness later fails or the head changes. This metadata does not change acceptance timing or final readiness revalidation.

The client workflow listens for newly created pull request comments whose body is exactly `/merge`. The commenter must have OWNER, MEMBER, or COLLABORATOR association, or be a Bot whose immutable ID matches the pull request author. This Bot exception only forwards a request. The server independently requires an enabled repository, an allowed bot merger, and every commit authored by that bot, followed by current approval, policy and CI checks. `repositories[].merge.allow_bot_requests: false` rejects Bot requests for a repository; no repository is restricted by name. See the [repository policy contract](policy-check.md#effective-repository-policy-resolution). Approval and recheck comments retain their association requirement.

`bun e2e/run.ts --ref <sha> --feature merge` exercises the merge scenarios against the testing repositories, including an explicitly approved workflow change and its exact merged content.

A deployed server workflow that omits workflows write from its final merge token cannot merge the workflow change that upgrades that token. If `controlled-merges` permits only the Server App, an operator merge cannot bypass that restriction. Bootstrap requires a concrete, separately authorized recovery procedure under [break glass](repo-settings.md#break-glass), with the affected settings saved and protection restored afterward. This specification does not authorize changing App permissions or disabling protection.

## Repository permission for Bot requests

The runtime accepts optional `repositories[].merge.allow_bot_requests`. Omission permits consideration under global Bot trust. `false` rejects Bot requests independently of global `trust.bot_mergers` membership and sensitive-path exemptions. The first matching repository entry supplies this setting. `true` still requires membership by immutable ID, ownership of the PR and every effective commit identity, current approval, effective policies, and required checks. The Server App executes every accepted merge regardless of who requested it.

Server operations share a concurrency group only with requests of the same kind for the same pull request, so a waiting `/merge` does not block `/approve`, `/recheck` or policy-check, and both can be posted together. Every readiness validation and the final revalidation use the current effective repository settings. Revoking Bot permission while a request waits must prevent its merge. Explicit protection for the server and actions repositories uses `allow_bot_requests: false` together with all-path sensitivity and no exemptions. Those entries must stay in the Server configuration; the runtime no longer adds this protection by name. Any subsequent relaxation requires a separate configuration diff and live verification.

A repository with `allow_bot_requests: false` rejects Bot requests before acceptance, without a rocket or receipt. Revocation after acceptance aborts readiness or final validation and posts the existing failure receipt. Human merger authorization is unaffected by this Bot setting.
