# Merge

`/merge` asks csm-ci to squash-merge the current head of an open pull request. The command takes no argument. It is accepted only from an account listed in `trust.mergers`, or from a bot listed in `trust.bot_mergers` when that bot authored the pull request and every commit.

The server checks the pull request state and the S5 trust rules before waiting. Every readiness validation reloads the configuration from the server repository's current default branch and confirms that the repository still enables merge. It then re-reads the pull request and command comment, evaluates the current policies against GitHub state, checks that the latest review from the configured approver is an approval for the pinned head, and verifies each configured required check by name and GitHub App ID. A moved head, invalidated comment, removed merger, changed policy, or failed trust check aborts the request. Readiness polling runs every 30 seconds until `merge.deadline_minutes` expires.

Notification tokens have issues and pull-requests write access because GitHub requires pull-request permission for PR comment reactions and receipts; they have no contents write access. The server mints fresh read and notification tokens after readiness succeeds, then mints its final token with contents, pull-requests, and workflows write access for the target repository. This final token includes workflows write for every ready pull request so approved `.github/workflows/**` changes can merge without a separate path-detection decision. Read and notification tokens have no workflows write access.

The server revalidates readiness before calling GitHub's squash merge endpoint with the pinned head SHA. HTTP 405, 422, and 503 responses are retried only after another complete validation. HTTP 409 fails immediately. A successful response must report `merged: true`. The additional permission does not bypass trust, command evidence, approval, policies, or required checks, and does not change securefix's `allow_workflow_changes` setting.

The squash commit uses the pull request title and body. Duplicate `Co-authored-by` lines in the body are removed. The server posts a receipt containing `<!-- csm-ci:merge:<comment_id> -->` after an accepted command succeeds or fails. Requests rejected before acceptance do not receive a receipt. If a long wait fails after the initial notification token expires, the workflow mints a fresh notification token and retries the idempotent failure receipt. A receipt authored by the Server bot prevents replay.

The client workflow listens for newly created pull request comments whose body is exactly `/merge`. The commenter must have OWNER, MEMBER, or COLLABORATOR association, or be a Bot whose immutable ID matches the pull request author. This Bot exception only forwards a request. The server independently requires an enabled repository, an allowed bot merger, and every commit authored by that bot, followed by current approval, policy and CI checks. The existing runtime forbids Bot mergers on the server and actions repositories. The [repository policy contract and staged migration](first-release-plan.md#repository-policy-overrides-and-staged-migration) replace that fixed rule with explicit configuration after separate implementation and deployment. Approval and recheck comments retain their association requirement.

`bun e2e/run.ts --ref <sha> --feature merge` exercises the merge scenarios against the testing repositories.

A deployed server workflow that omits workflows write from its final merge token cannot merge the workflow change that upgrades that token. If `controlled-merges` permits only the Server App, an operator merge cannot bypass that restriction. Bootstrap requires a concrete, separately authorized recovery procedure under the [cutover runbook](cutover.md#rollback-for-one-repository), with the affected settings saved and protection restored afterward. This specification does not authorize changing App permissions or disabling protection.

## Repository permission for Bot requests

The approved contract adds optional `repositories[].merge.allow_bot_requests`. Omission defaults to `true`. `false` rejects Bot requests independently of global `trust.bot_mergers` membership and sensitive-path exemptions. The first matching repository entry supplies this setting. `true` still requires membership by immutable ID, ownership of the PR and every effective commit identity, current approval, effective policies, and required checks. The Server App executes every accepted merge regardless of who requested it.

Every readiness validation and the final revalidation use the current effective repository settings. Revoking Bot permission while a request waits must prevent its merge. Explicit protection for the server and actions repositories uses `allow_bot_requests: false` together with all-path sensitivity and no exemptions. Deploy compatible configuration readers and those entries before removing the legacy restrictions. Any subsequent relaxation requires a separate configuration diff and live verification.
