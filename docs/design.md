# Design

This document explains how csm-ci-actions is built and why. The operation pages ([approve](approve.md), [merge](merge.md), [policy-check](policy-check.md), [securefix](securefix.md), [release](release.md), [release-pr](release-pr.md), [repo-settings](repo-settings.md)) define each operation's behavior. This page defines the rules every operation shares.

## Principles

- **The server trusts nothing the client sends.** A request label is only a locator. The server re-reads every fact from the GitHub API with its own token, so it needs no proof of the client run's provenance. The securefix diff is the one piece of client content, and [S4](#s4-binding-of-the-paths-the-server-writes) binds it to its source.
- **Strong credentials stay in one place.** Write credentials live only in the server repository's `csm-ci` environment. Client repositories hold a key that can do nothing but create a request label on the server.
- **One configuration, no personal values in code.** Every App ID, user ID and policy comes from the server's `csm-ci.yaml`, validated strictly. Identities are matched by immutable ID, never by login.
- **Fixed, small scope.** Operations and policy types are built in and configured declaratively. A behavior is added only with a concrete need, and the shortest path that satisfies the specification wins. There are no control revisions, runtime distribution, alternate protocols or external scripts.
- **Decide late, write once.** Commands take no arguments; the server pins the head it observed. Write tokens are minted only after validation passes, with the least permissions the step needs, and every write is preceded by a final revalidation against the pinned state.
- **Client code never meets a credential.** Release builds run the client's code in an unprivileged job. Signing and attestation happen in a separate job that runs no client code.
- **Server-made commits are recognized by structure, not trust.** The Server bot is never a trusted committer. A commit counts as server-made only when its identity and GitHub signature prove it, and every server write path is bound as described in S4.

## Architecture

```
client repo                         server repo (csm-ci-server)
caller workflow (a few lines)       csm-ci.yaml (the only configuration)
 └ uses csm-ci-actions/             .github/workflows/csm-ci.yml (a few lines)
   .github/workflows/client-*.yml@sha   on: label created
     ├ (comment ops) pre-filter the     → uses csm-ci-actions/.github/workflows/server.yml@sha
     │  body and commenter                ├ intake job: validate → normalized output
     ├ create-github-app-token            ├ op job (environment: csm-ci, serialization key
     │  (Client App, installed on         │   comes from the intake's normalized output)
     │   the server repo only,            ├ create-github-app-token (Server App,
     │   issues:write)                    │   one target repo, least privilege per step)
     └ create label                       └ delete label (always)
       name: csm-ci-<op>-<rand>
       desc: owner/repo/<args>
```

securefix is the one exception on the client side. Its changes are generated by the caller's own steps, so its caller cannot be a reusable workflow. The caller runs the composite action `actions/client/securefix` after those steps in the same job. The action packages the changes, uploads the artifact, mints the Client App token and creates the label.

## Technology choices

- **Build.** bun installs, tests and builds. `bun build --target=node` writes one file per action, `dist/<side>-<name>.js`, which runs as a `node24` JS action. `dist/` is committed, and CI checks that a clean build leaves `git status --porcelain dist/` empty.
- **Runtime dependencies** are limited to `@actions/core`, `@octokit/core`, `@octokit/plugin-rest-endpoint-methods`, `@octokit/plugin-paginate-rest`, `zod`, `yaml` and `picomatch`. Adding one requires a concrete need that the existing set cannot meet.
- **App tokens** come from the official `actions/create-github-app-token`. Private keys never reach code in this repository.
- **Loading actions from a reusable workflow.** Server jobs check out `job.workflow_repository` at `job.workflow_sha` into `.csm-ci-actions` and use `./.csm-ci-actions/actions/<name>`, so actions always come from the called workflow's revision. The five client reusable workflows instead call their composite through `uses: $/actions/client/<name>` and are covered by the generated `.github/workflows/actions.lock`, so clients that enforce action lockfiles can use them.
- **Secrets** are passed by explicit name. Each reusable workflow declares its secrets, and callers map each one to the same name; supported callers do not use `secrets: inherit`. Credentials never pass through inputs, outputs, artifacts, logs or command arguments. [setup.md](setup.md) lists the mappings.
- **Static checks.** Every external action is pinned to a full SHA. CI runs jactionlint with `--online`, which includes the actionlint and zizmor checks and detects impostor-commit pins. Event values reach scripts only through `env`. Server workflows use no cache.
- **Artifacts** carry the securefix diff, and the release source, build outputs and public verification key between release jobs. They never carry credentials.
- **License:** MIT.

## Layout

```
src/lib/                shared logic (config, request, github, trust, policies, ...)
src/<side>-<name>/      main.ts → dist/<side>-<name>.js
actions/client/<name>/  approve, policy-check, merge, securefix,
                        release-prepare, release-publish
actions/server/<name>/  intake, approve, policy-check, merge, securefix,
                        release-plan, release-tag, release-build, release-assets,
                        release-publish, repo-settings, check-config
.github/workflows/      server.yml, server-check.yml,
                        server-repo-settings.yml (+ server-repo-settings-target.yml),
                        client-<name>.yml (approve, policy-check, merge,
                        release-prepare, release-publish)
docs/, e2e/
```

- Actions live exactly one level below `actions/client/` (they run in a client repository) or `actions/server/` (they run in the server repository).
- Each client action mints its own Client App token and creates its own request label. Shared code lives only in `src/lib`, so one operation can change without affecting the others.
- Each `client-<name>.yml` is a thin wrapper around `actions/client/<name>`. securefix has no reusable workflow.
- A policy is a zod schema member of `PolicySchema` plus an evaluator. Adding one takes an evaluator file, a schema member and an entry in the `EVALUATORS` map.

## Security design

### S1. Trust boundary

- The server's decisions do not depend on values passed from the client or on the integrity of the client run.
  - The label description is used only as a locator.
  - The server re-fetches every fact from the GitHub API with the Server App token.
- The one exception is the content of the securefix diff. S4 binds it.

### S2. Intake (`src/lib/request.ts`, a separate intake job)

1. The event repository ID matches the server repository.
2. The label's `sender.id` is the Client App bot, and `type == Bot`. The workflow `if:` also filters on this first.
3. The label name matches `^csm-ci-<op>-[a-z0-9]+$` and is at most 50 characters. `<op>` is one of the operations. The description holds the numbers defined per request kind in `REQUEST_KINDS`: one for an automatic request (a PR number or a run ID), two for a comment command (a PR number and a comment ID).
4. The description is lowercased and validated with a per-operation regex. Numbers have no leading zeros.
5. The repository is in `repositories[]`, the operation is enabled for it, and its owner is in `owners`.
6. The live label is re-fetched and must match, and `GITHUB_RUN_ATTEMPT == 1`.
7. The normalized `{kind, repo, number}` is emitted as a job output and used as the operation job's `concurrency` key, so spelling variants cannot run in parallel. `approve` and `policy-check` share one key per pull request because both publish the policy check and failure reports.
8. The label is always deleted.

### S3. Trust rules (`src/lib/trust.ts`)

- A pull request has fewer than 250 commits, and the last item of listCommits matches the pinned head.
- Every commit is `verification.verified`.
- The effective identity is the committer's user ID. A commit whose committer and author are both null is rejected.
- For a `web-flow` commit, the effective identity is the author, confirmed with GraphQL `committedViaWeb`, `signature.isValid` and `wasSignedByGitHub`, and matching the REST author.
- A **Server bot commit** is server-made, and trusted, only when `author.id == server_bot_id`, the committer is `web-flow`, and `wasSignedByGitHub` holds. This is sound because every server write path satisfies S4. Trailers are not used.
- The trust rules are always evaluated, whatever `policies` contains.

### S4. Binding of the paths the server writes

- **securefix PR mode**
  - `run.pull_requests` has exactly one entry, it is the target PR, and its `base.ref` is the default branch.
  - The request is rejected if the head branch has two or more open PRs. This closes the path where another PR from the same branch to a malicious base runs the attacker's workflow.
  - The server does not create PRs or edit their title or body in this mode.
- **securefix route mode**
  - `run.path` matches the route's workflow, the event is `push` or `workflow_dispatch`, and the run's head is the current head of the default branch.
  - Changes stay within the route's `paths`. A `version-only` file may change only lines matching `^\s*"?version"?\s*[=:]`, one rule for every manifest format. `.release-version` must be semver.
- **Server-owned branches** (`release/next`, `csm-ci/repo-settings`)
  - Every commit after the merge base must be server-made and within range.
  - A new commit is built on a temporary branch at the head of the default branch, and the owned branch is moved to it in one leased update, so the branch never equals its base and its open PR stays open.

### S5. Comment commands (`/approve`, `/merge`, `/recheck`)

- **Client side**: only a comment that passes the body and commenter pre-filter mints a token, which prevents label spam from fork commenters.
  - `/approve` and `/recheck` require OWNER, MEMBER or COLLABORATOR association.
  - `/merge` accepts those associations, or a Bot whose immutable comment-author ID equals the PR author's ID in the issue event. Forwarding a Bot request grants nothing; the server still requires `trust.bot_mergers` membership, ownership of the PR and every commit, current approval and checks, and the repository's permission for Bot requests.
- **Server-side acceptance** for `/approve` and `/merge`
  - The comment belongs to the target PR, and its body matches the command exactly.
  - It is unedited (`updated_at == created_at` and GraphQL `lastEditedAt == null`) and no more than 60 minutes old.
  - The author's ID and `type` match.
- An accepted comment gets 🚀. For `/approve` and `/merge`, on success and failure alike, the server posts a receipt with the marker `<!-- csm-ci:<op>:<comment_id> -->`.
- **Replay**: a request is rejected if a marker authored by the Server bot already exists. A collaborator who deletes the marker can only retry the same command against the same head, which does no harm.
- **Head pinning**: commands take no argument. The server pins the head it observed and rejects the request when a `head_ref_force_pushed` event follows the comment or the head's committer date is newer than the comment. A short SHA argument could be brute-forced and a full one is impractical to type. `/approve` requires every commit to come from a trusted committer, so a swapped commit can only come from one.
- **Kill switch**: while a self-merge request waits, the server re-reads the comment on every poll and aborts if it was edited or deleted. A `/merge` that enabled platform auto-merge checks the comment only at acceptance; see [Merge](merge.md#platform-auto-merge).
- **`/recheck`** re-runs the policy check and the automatic approval decision for the current head after a transient GitHub failure. Its result depends only on current API state, so it is idempotent. It skips the edit, 60-minute and replay checks, posts no receipt, and never forces an approval.

### S6. Placement of secrets and permissions

- **Environment `csm-ci`** (deploys from the default branch only) holds the Server App key, the Approver App key and, when enabled, the Terraform provider signing credentials.
- The release build job declares no environment.
- **Client App** is installed only on the server repository, with `issues: write`.
- **Server App** permissions:
  - `contents: write`, `pull_requests: write`, `issues: write`, `checks: write`, `actions: read`.
  - `workflows: write`: minted only when securefix allows workflow changes, for managed files, and on the final merge token after readiness succeeds. Read and notification tokens never receive it.
  - `administration: write`: minted only in repo-settings jobs. Unlike an admin PAT, the token expires in an hour, can be limited to one repository, is not tied to a person and needs no renewal.
- **Approver App** needs `contents: write` installed so its approval counts toward required approvals; its tokens are minted with `pull_requests: write` only.
- **Rulesets** (synced by repo-settings):
  - `integrity` (default branch): `deletion`, `non_fast_forward`, `required_linear_history`, `required_signatures`. No bypass.
  - `review-and-checks`: one approval, `dismiss_stale_reviews_on_push`, `csm-ci/policy` from the Server App and the configured `required_checks`, squash only. Branches need not be up to date, because `/merge` does not update them.
  - `controlled-merges`: the `update` rule only. The only bypass is the Server App with `bypass_mode: pull_request` (`always` would allow direct pushes).
  - `release-tags` (`refs/tags/v*`): forbids `creation`, `update` and `deletion`. The only bypass is the Server App.

### S7. Known compromises

- The Client App key lives in a client repository secret, so anyone with write access there can create any label. S1 limits the impact. The securefix composite holds this key in the job that ran the caller's fix tools for the same reason.
- An App's approval counts only when the App has `contents: write`, so the Approver App key can also push. It sits in the same environment as the Server App key, which already has `contents: write`, so a leak changes little.
- For required checks produced by GitHub Actions, a PR author with write access can modify the workflow. The real gates are the approval and `csm-ci/policy`.
- Fork PRs are out of scope for securefix. approve and policy-check run on `pull_request_target` but never check out PR code.
- Head pinning cannot detect a push by a trusted committer that forged `committedDate`.
- The final merge token carries `workflows: write` for every ready PR, to avoid a separate path decision before minting it. It is used only to merge the pinned head after final revalidation, and does not allow securefix workflow changes when `allow_workflow_changes` is false.
- **All server jobs share the Server App key**, so a compromise of any job can mint an `administration: write` token. Narrowing token permissions per job is operational discipline, not a boundary. Separating it would need a third App and environment.

## Naming list

This is the single source for names. The implementation, docs and setup wizard use these names.

- The namespace is `csm-ci` for Apps and environments, and `CSM_CI_` for secrets and variables.
- App credentials are a pair of `CSM_CI_<ROLE>_APP_CLIENT_ID` (a variable, passed to `client-id` of `actions/create-github-app-token`) and `CSM_CI_<ROLE>_APP_PRIVATE_KEY` (a secret). A PAT is `CSM_CI_<ROLE>_TOKEN`.
- `<ROLE>` is the App name without `testing-csm-ci-` or `csm-ci-`, in upper snake case. Example: `testing-csm-ci-untrusted-committer` → `UNTRUSTED_COMMITTER`.
- Uses are told apart by environment; variable names get no qualifier such as `E2E_`.
- The App name limit is 34 characters.
